Here's a scenario I see with customers all the time. An environment gets a monthly pool of Copilot Credits. One agent goes viral internally, say an HR assistant that half the company starts using in the same week, and it quietly eats the credits that every other agent in that environment was counting on. Nobody notices until the other agents stop answering.

Microsoft just shipped the control I've been asking for: spending policies for Copilot Studio in the Microsoft 365 admin center, with a monthly limit per environment and a limit per agent. Resource and environment spending policies are in public preview. Identity-scoped policies (per user or group) are marked coming soon.

I went through the whole flow in my tenant. My take: the environment budget is the headline, but the per-agent limit is the setting that will actually save you from the 2 a.m. "why did everything stop" call.

1. What really changes: Copilot Studio cost management moves into the Microsoft 365 admin center

Until now, Copilot Studio capacity lived in the Power Platform admin center: environment credit allocation, agent credit limits, overage notifications. That doesn't disappear. What's new is that the Microsoft 365 admin center (MAC) now has Copilot > Cost management, with three tabs: Overview, Configuration and Consumption.

Under Configuration > Add spending policy you pick a scope:

  • Identity: the people who sign in and use the agents.
  • Resources: specific resources, regardless of who runs them. Inside it, Specific resource (individual agents you pick by name) or Resource collection (all usage inside the environments you choose).

The opt-in is the policy itself. According to Microsoft Learn, there's no migration step: once a MAC resource-based policy is linked to an environment, it takes precedence for that scope, and Power Platform capacity allocations and linked billing plans no longer apply to that environment. Remove the environment (or delete the policy) and the Power Platform configuration resumes automatically.

2. The underrated detail: "Limit monthly spending per agent"

On the Limits and alerts step there are two separate blocks, and this is where it gets good:

  • Set the monthly spending limit for this policy: the cap for the whole policy. I set $400 (≈ 40,000 credits).
  • Select monthly budget limits for agents > Limit monthly spending per agent: the UI describes it as preventing runaway usage by a single agent with a uniform limit across all agents in the policy. I set $50 (≈ 5,000 credits).

That second number is the one that protects your other agents. With only an environment cap, the popular agent still drains the pool and everyone hits the wall together. With a per-agent cap, the popular agent stops at its own ceiling and the rest keep working.

Things I only saw by clicking through:

  • You type limits in USD, and the screen converts them to credits. The UI warns that limits are saved in credits, so their currency value can change with your pricing.
  • The wizard enforces a minimum based on the number of resources in the policy. For my environment it asked for at least $310 (≈ 31,000 credits) at policy level and $20 (≈ 2,000 credits) per agent, and showed a "recommended" value based on industry usage trends.
  • When the limit is reached, the screen says the resource (for example, an agent) can no longer run until credits reset on the 1st of next month. That's a hard stop, so size it with care.
  • Define alerts sends a daily email summary to users or mail-enabled security groups. You get a policy threshold (I used 80% of limit) and a separate Alert when an agent's monthly spending reaches field.

3. Funding: prepaid, pay-as-you-go and chargeback via Azure

The Billing method step uses the default subscription, and you can override it with Use Capacity packs (the prepaid Capacity Pack credit bundle) or Use Pay-as-you-go, which bills a connected Azure subscription. The screen states that prepaid credits are used first before switching to pay-as-you-go. Microsoft also notes that policy limits apply to both prepaid and PAYG usage.

For me the business angle is chargeback: linking a policy to an Azure subscription so each department sees and owns its costs. That's the conversation every CFO wants to have about AI agents, and it's finally a setting instead of a spreadsheet.

4. Risk and governance: read the hierarchy before you click "All environments"

Two things will surprise admins.

First, the default. When I chose Resource collection, the wizard pre-selected All environments. Microsoft Learn is explicit: start with Specific environments, because All environments moves every environment in the tenant at once and removes their Power Platform capacity allocations and linked billing plans.

Second, the order of precedence, as documented on Learn:

  1. Microsoft 365 admin center policies come before Power Platform admin center controls for the usage they cover.
  2. Resource-based comes before identity-based. An HR agent's resource policy applies regardless of who runs it.
  3. Among policies of the same type, the highest applicable limit applies. Limits are not combined. The wizard repeats it: the most permissive policy is enforced.
  4. If an agent hits its agent-specific limit, usage doesn't fall back to the user's identity-based policy.

Also note the scope gaps: resource-based policies don't cover AI Builder features or the credits they consume (including prompts used as tools, in topics or as agent flow nodes). And apps and workflows don't appear in the agent picker, so to cover them you create a policy for their environment.

5. What admins should do now

  • ☑ Assign the new roles first. Power Platform or Dynamics 365 Administrators get AI Administrator to manage spending policies (it isn't granted automatically). Environment Administrators get AI Reader to view consumption. Global admins: no change. Makers: no new role.
  • ☑ Pilot with Specific environments, never All environments on day one.
  • ☑ Set a policy limit and a per-agent limit. Use the wizard's minimum and recommended values as a starting point.
  • ☑ Turn on alerts for a mail-enabled security group, not one person.
  • ☑ Decide prepaid vs PAYG per policy, and link an Azure subscription where you need chargeback.
  • ☑ Allow up to 12 minutes after linking an environment for the policy to apply.

6. What makers should do

Makers don't get a new role, but they get visibility. Microsoft describes consumption views across the build cycle in Copilot Studio: Preview (near-real-time estimates for design decisions), History (conversation-level estimates to find expensive or failed paths), Evaluate and Monitor (reconciliation against processed usage, with a reporting delay). Some of these views depend on rollout.

My advice: before you ask your admin for a bigger cap, open History and find the expensive path. A per-agent limit turns "we'll optimize later" into a real deadline.

What I'm watching

  • Identity-scoped spending policies (per user or security group), marked coming soon. This is how you'll fund makers to experiment without opening the whole tenant.
  • Recommended limits, recommended roles and roles set up in code, which Microsoft lists as early 2027 (planned).
  • Rollout: in the Tech Community comments, at least one admin reported Copilot Studio didn't yet appear when creating a spending policy. Check your tenant before you plan a change window.
